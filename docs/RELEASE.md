# Releasing Novila to Google Play

This is the one-time setup and the recurring procedure for publishing Novila as a signed
App Bundle to Google Play from CI. The pipeline itself lives in:

- `.github/workflows/release.yml` — builds the release AAB and publishes it to a Play track
- `scripts/generate-release-keystore.sh` — one-time local generation of the upload keystore
- `scripts/bootstrap-play.sh` — one-time Google Cloud / Workload Identity Federation setup
- `app/build.gradle.kts` + `build-logic` (`AndroidApplicationConventionPlugin`) — Gradle Play
  Publisher (`com.github.triplet.play`), track `internal`, App Bundles, Application Default
  Credentials

The tester pipeline (`distribute.yml`, Firebase App Distribution) is separate and keeps
working unchanged; it shares the release keystore secrets so the signed release APK there and
the AAB here are signed with the same upload key.

## How signing works (read this first)

Google Play **App Signing** is the default and assumed setup:

- The **app-signing key** is generated by Google Play and never leaves Google. Every install
  from Play is signed with it. You cannot lose it and you never handle it.
- The **upload key** signs the AAB that CI produces; Google re-signs it with the app-signing
  key on upload. CI needs only this key, stored as GitHub Actions secrets.

So the keystore this pipeline uses is an **upload keystore**, not the app-signing keystore.
If the Play Console offers "Enroll in Google Play App Signing" for a new app, enroll: the
first AAB upload through the Console starts that flow automatically.

**If an upload keystore already exists** (e.g. the `NOVILA_RELEASE_KEYSTORE_BASE64` secret is
already set on the repository, or a `.jks` file exists outside git): do **not** generate a new
one and do not replace the secret. A different upload key causes Play to reject the upload
unless an upload-key reset is requested (see below). The repo itself contains only
`app/debug.keystore`, which is the debug key checked in on purpose and never used for
release.

### Upload-key reset flow (lost or compromised upload key)

1. Play Console → **Setup** → **App integrity** → **App signing** → **Request upload key
   reset** (or the equivalent under *Advanced → App signing*). Google support verifies the
   request out-of-band; a key reset is a manual, one-time-per-key process.
2. Generate a new upload keystore with `scripts/generate-release-keystore.sh`, back it up,
   and update the GitHub secrets to the new keystore and passwords.
3. Until the reset is approved, Play rejects uploads signed with the new key — so treat the
   upload keystore as valuable and keep the backup.

## One-time setup

All of it is done once, from a phone if you like (Google Cloud Shell has `gcloud`).

### 1. Google Play app

1. Create the developer account and the app in the [Play Console](https://play.google.com/console)
   (`se.novila`), fill in the minimum listing, and upload the **first AAB manually** via the
   Console. That first upload enrolls the app in Play App Signing and creates the initial
   release; after that CI can take over.
2. The app must be at least in a draft state with the package name `se.novila` (the debug
   package `se.novila.debug` goes to Firebase only and never to Play).
3. Play requires strictly increasing version codes. The workflow sets `versionCode` to the
   **run number of `release.yml`**, which starts at 1. If the manual first upload already used
   version code 1 (a local build without `VERSION_CODE` gets 1), delete that draft release in
   the Play Console before the first CI publish, or the first run fails with a version
   conflict — on purpose, never silently.

### 2. Play service account and Workload Identity Federation

Run in Google Cloud Shell (the same Google Cloud project as Firebase is recommended):

```sh
./scripts/bootstrap-play.sh <project-id>
```

The script is idempotent and:

1. enables the **Android Publisher API** on the project,
2. creates the service account `github-play@<project>.iam.gserviceaccount.com`,
3. creates the Workload Identity Federation provider `novila-play` in the `github` pool,
   whose attribute condition only accepts jobs running in the GitHub environment **`play`**
   of this repository,
4. grants the pool's federated principals permission to act as that service account,
5. sets the GitHub variables `GCP_PLAY_WORKLOAD_IDENTITY_PROVIDER` and
   `GCP_PLAY_SERVICE_ACCOUNT` (or prints them for you to add by hand).

No JSON key is created or needed. This is the OIDC + Workload Identity Federation path:
the release job exchanges its GitHub OIDC token for short-lived Google credentials, so no
long-lived secret exists anywhere.

### 3. Grant the service account Play permissions (least privilege)

Play Console → **Users and permissions** → **Invite new user** → paste
`github-play@<project>.iam.gserviceaccount.com`:

1. Under **App permissions**, choose the Novila app only.
2. Grant the permission set that can release to **testing tracks only** — in the current
   Console: *Release to testing tracks* (or the **Release manager** role restricted to the
   Novila app, which excludes production releases). This lets CI publish to *internal*,
   *alpha* and *beta*, but **not** to *production*: a production rollout stays a deliberate
   step, done by promoting in the Console (or by widening the permission on purpose later).
3. Leave everything else (financial data, subscriptions, payments, admin) unchecked.

The service account needs no GCP project role beyond existing as itself; the Play permission
is granted entirely in the Play Console.

### 4. GitHub environment and secrets

1. Repo **Settings → Environments → New environment**: name it `play`. Optionally add
   required reviewers so publishes need a click of approval — the WIF provider only accepts
   tokens from jobs in this environment.
2. Under **Settings → Secrets and variables → Actions**, set (same names as
   `distribute.yml` uses for the signed release APK):

   | Name | Kind | Value |
   |---|---|---|
   | `NOVILA_RELEASE_KEYSTORE_BASE64` | Secret | `base64 -w0 novila-upload.jks` output |
   | `NOVILA_RELEASE_STORE_PASSWORD` | Secret | the keystore password |
   | `NOVILA_RELEASE_KEY_PASSWORD` | Secret | the key password (PKCS12: the same password) |
   | `NOVILA_RELEASE_KEY_ALIAS` | Variable | the alias, default `novila` |
   | `GCP_PLAY_WORKLOAD_IDENTITY_PROVIDER` | Variable | printed by `bootstrap-play.sh` |
   | `GCP_PLAY_SERVICE_ACCOUNT` | Variable | printed by `bootstrap-play.sh` |

   If the first three are already set, they are the live upload credentials — keep them.

### 5. Generate and back up the upload keystore (once)

On any machine with a JDK (`keytool`), **not** on the repo machine if avoidable:

```sh
./scripts/generate-release-keystore.sh
```

It creates `novila-upload.jks` (RSA 4096, valid 10000 days), refuses to overwrite anything,
and prints the exact `base64` line and secrets to set. Then, in this order:

1. **Back it up now** (see *Secrets backup* below): the `.jks` file, the keystore password
   and the key password in a password manager with one strong master password.
2. Set the GitHub secrets as printed.
3. Delete the local file: `rm novila-upload.jks`. `.gitignore` already excludes `*.jks` and
   `*.keystore`; nothing keystore-shaped may ever be committed.

## Cutting a release

Two ways, both gated so nothing publishes by accident:

- **Tag**: push a version tag — `git tag v0.1.42 && git push origin v0.1.42`. The workflow
  runs only for `v*` tags on this repository, never for pull requests or forks.
- **Manual**: Actions → *Release to Google Play* → *Run workflow* from **main**, picking the
  track (default `internal`). A manual run from any other branch is rejected.

The job runs in the `play` environment (add required reviewers there for a manual approval
gate). It builds the release AAB (R8) signed with the upload key, with
`versionCode` = workflow run number, and publishes it to the chosen track via Gradle Play
Publisher (`publishReleaseBundle --track …`). Release notes are generated from the merged
PRs since the previous release run and capped at Play's 500 characters.

Promote from *internal* to beta/production in the Play Console — that step is deliberately
not automated.

### JSON-key fallback (not used, documented for completeness)

If Workload Identity Federation ever proves impractical, GPP also accepts a service-account
JSON key: download a key for the Play service account in GCP, store its **contents** in a
GitHub secret (never in git), decode it to a file in the workflow and point GPP at it with
`play { serviceAccountCredentials.set(file("…")) }`, or put the contents in the
`ANDROID_PUBLISHER_CREDENTIALS` environment variable. This is the fallback only: a JSON key
is long-lived, cannot be scoped to one environment, and is exactly what WIF removes.

## Secrets backup (human procedure)

Everything below exists in exactly one or two places; losing it means an upload-key reset:

1. Use a password manager with **one strong master password** (1Password, Vault, Bitwarden
   …), protected by the master password and, where available, 2FA.
2. Store in it, as one entry "Novila release":
   - the upload keystore file (as an attachment; `generate-release-keystore.sh` prints the
     base64 you can paste into a secure note),
   - the keystore password,
   - the key password,
   - the key alias,
   - the Play service account email and the GCP project id.
3. Verify the backup restores: decode the base64 into a file and run
   `keytool -list -keystore file.jks` with the stored password.
4. **Never** commit keystore files, keys, passwords or JSON credentials to the repository.
   `.gitignore` blocks `*.jks`/`*.keystore`; GitHub secrets are for CI, the password manager
   is for humans.

## Guardrails (what this pipeline will not do)

- No `pull_request` trigger, no fork access: the workflow only runs for `v*` tags on
  `joeldenke/Novila` and for manual dispatches from `main`, inside the `play` environment.
- No secrets in logs: configuration steps print names of missing variables, never values;
  the keystore lives only in `$RUNNER_TEMP` and is deleted in an `always()` step.
- No production publishes: the default track is `internal`, and the Play service account has
  testing-tracks permission only.
- No long-lived Google credentials: authentication is OIDC + Workload Identity Federation
  (`scripts/bootstrap-play.sh`); no service-account JSON is stored.
